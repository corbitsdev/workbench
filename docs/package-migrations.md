# Package migrations

Convention for any package under `packages/` that owns its own product
tables.

## The rules

- **Literal SQL, not codegen.** Every migration is a plain string in a
  `{ name, sql }[]` array, hand-written and reviewed as-is — never a
  schema diff generated by `drizzle-kit` at apply time. What a reviewer
  reads in the PR is exactly what runs against the database.
- **A ledger table the package owns.** Each package tracks which of its
  own migrations have run in a table named for itself (e.g.
  `webhook_triggers_migrations`) — never the platform's own `@intx/db`
  drizzle journal, and never `scripts/db-setup.ts`'s own migration
  tracking, which only covers the platform. If the package is ever
  extracted into its own repo, its migration history goes with it.
- **Every package owns a schema named for itself.** No package table
  lives in `public` — that belongs to `@intx/db` alone. A package's
  tenant/principal columns are plain text ids, not foreign keys, so
  which schema a table lives in is never load-bearing for that
  reference; it only matters for keeping the package extractable.
- **Every migration is transactional.** A migration's SQL and its ledger
  `INSERT` run inside one `sql.begin(...)` transaction, so a failure
  partway through never leaves a half-applied table with no ledger row
  to explain it.
- **A session-level advisory lock guards the whole run**, so two hub
  replicas booting at once don't race the same ledger insert.

Mechanics — schema/ledger bootstrap, the transactional apply loop, and
the advisory lock — live once in `@corbits/migration-runner`'s
`applyPackageMigrations`; a package's own `migrations.ts` supplies only
its schema name, ledger table name, and literal migration array. See
`packages/webhook-triggers/src/migrations.ts` for the reference shape.

## Wiring a new package in

`scripts/db-setup.ts` imports each installed package's
`applyXMigrations(databaseUrl)` and calls it, in an explicit literal
list, right after the platform's own migrations — no discovery magic,
no globbing. Add the new package's entry to that list.

A package that ships its own independently-owned migration runner as
part of a larger engine (its own schema, its own connection handling —
`@corbits/mailbox` is the example) can instead be wired as a thin
delegate: `scripts/db-setup.ts` opens a connection and calls the
package's own exported runner, with no opinion on what SQL it runs.
Reach for this only when the package already has such a runner, never as
a shortcut to skip writing a ledger table.

## Why not `drizzle-kit` codegen

Drizzle is used as a query builder and for type definitions, but package
migrations are never generated by pointing `drizzle-kit` at a schema and
diffing. A generated migration reviewed as a schema diff, with the
actual SQL produced later by codegen, lets the reviewed artifact and the
applied artifact drift. Literal SQL closes that gap.
